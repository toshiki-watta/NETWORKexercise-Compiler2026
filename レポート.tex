\section*{(1) 最終的に作成した記号表の構造と操作関数の仕様}

\subsection*{1. 記号表の構造とコンパイラにおける役割}
記号表（シンボルテーブル）は、原始プログラム中に出現する変数や手続きなどの識別子（\texttt{IDENTIFIER}）を管理し、その属性や割当番地、スコープを保持するための極めて重要なデータ構造である。
本コンパイラの実装においては、ヘッダファイル \texttt{symtab.h} およびソースファイル \texttt{symtab.c} に独立したモジュールとして管理機構を分離・実装している。

現在割り当てられている記号表は、最大登録数 \texttt{MAXSYMS}（32個）を上限とする1次元の構造体配列である。
識別子名となる文字列 \texttt{char name[MAXIDLEN+1]} をキーとして保持し、配列のインデックスそのものが、目的計算機（仮想マシン \texttt{sr}）における大域変数の固定データメモリ番地（オフセットアドレス）に対応するマッピング構造を採っている。
また、数式評価時に動的に生成される一時確保用変数（\texttt{\_\_tmp0}, \texttt{\_\_tmp1} $\dots$）もこの記号表へ逐次追加登録され、一元的に番地管理が行われる。

さらに、今後の発展的な拡張機能である「手続き（\texttt{PROCEDURE}）処理」への対応を見据え、手続き名とその開始ラベルの対応関係を保持する配列 \texttt{proc\_label} を記号表配列と並列にマッピングさせることで、簡易的な手続き識別情報の管理を実現している。

\subsection*{3. 操作関数の仕様とアルゴリズム}
記号表の操作は、構文解析側から透過的に利用できるように以下の3つの関数によって定義されている。

\begin{itemize}
    \item \texttt{int sym\_install(char *name); } \\
    引数として渡された識別子名文字列（\texttt{name}）を走査し、すでに表内に同一名称の識別子が存在するかどうかを確認する。
    未登録である場合は、現在カウントされている空きインデックス位置へ識別子名を登録し、その配列番号（割当番地）を返す。
    もし既に登録済みである場合は、二重登録を防ぐため既存のインデックス番号をそのまま返す仕様である。
    \item \texttt{int sym\_lookup(char *name); } \\
    構文解析中に変数参照や代入文、あるいは条件式の評価文が現れた際、指定された識別子名が既に宣言されているかを逆引きするための関数である。
    記号表配列を前方から線形探索し、一致する名前が発見された場合はそのインデックス（番地）を返す。
    探索の結果、表内に存在しない識別子であった場合は宣言エラーとみなして \texttt{-1} を返すアルゴリズムを採っている。
    \item \texttt{void sym\_dump(void); } \\
    コンパイラ開発時およびプログラム検証時のデバッグ用関数である。
    原始プログラムの変数宣言ブロック（\texttt{outblock}）の解析が完了した直後に呼び出され、その時点で記号表に登録されているすべての識別子名とインデックス番号を標準エラー出力（\texttt{stderr}）へ一斉にダンプ出力する。
\end{itemize}

\subsection*{4. 手続き拡張への課題と二重構造化への展望}
現在の1次元配列による記号表の仕様は、すべての変数を大域変数（固定データ番地）として一列に管理する。
この構造は、単純な数式処理や制御構文（\texttt{if}, \texttt{while}）の処理においては破綻なく動作するものの、手続き呼び出し、とりわけ「再帰呼び出し」を正しく実現するにあたっては構造的な限界を有している。

手続きが再帰的に呼び出される場合、各呼び出し世代ごとに独立した局所変数（および引数）の領域が実行時スタック上に動的に確保されなければならない。
しかし現状の記号表では、大域変数と手続き内の局所変数を識別・隔離する「スコープ（属性）」の情報が欠落しており、同一の関数インデックスに対してすべての世代から固定番地アクセスが実行されてしまうため、再帰呼び出し時にローカル変数の値が上書き破壊される。

この課題を克服するためには、今後の発展的アプローチとして、記号表内に識別子の属性（大域変数 \texttt{K\_GLOBAL}、局所変数 \texttt{K\_LOCAL}、手続き名 \texttt{K\_PROCEDURE}）を区別するメンバを追加する必要がある。
その上で、図2に示すように記号表自体を「大域記号表」と「手続き局所記号表」の二重構造（あるいはスコープ深度による木構造・スタック構造）へと拡張し、識別子探索時には「まず現在コンパイル中の手続きスコープ（局所表）を逆順に探索し、発見されなかった場合のみ大域表を参照する」というシャドーイング対策を施した動的オフセット管理の導入が必須である。

\section*{(2) if文、while文のコンパイルの仕様}

\subsection*{1. 目的計算機における制御構文の実現原理}
原始言語が提供する \texttt{if} 文や \texttt{while} 文といった高水準な制御構文は、目的計算機（仮想マシン \texttt{sr}）の命令セットアーキテクチャにおいては直接実行することができない。
仮想マシンが持つジャンプ命令は、フラグ命令を参照して分岐を行う条件付きジャンプ命令（\texttt{jz}, \texttt{jnz}, \texttt{jge} 等）と、無条件に指定アドレスへ遷移する \texttt{jmp} 命令のみである。
そのため、コンパイラは構文解析の過程において、条件式の評価結果と動的に生成される「制御用ラベル」を巧みに組み合わせ、直線的なアセンブリ命令の列へと展開（コンパイル）しなければならない。
本コンパイラでは、ラベルの重複を防ぎ一意性を保証するため、\texttt{label.c} で提供される \texttt{new\_label()} 関数を利用してラベル番号を動的に払い出している。

\subsection*{2. if文のコンパイル仕様と制御フロー}
構造文解析関数 \texttt{statement()} 内で予約語 \texttt{IF} を検知した際、コンパイラはまず条件式の左辺を数式解析ルーチンを介してレジスタ \texttt{r0} に評価する。
その後、続く比較演算子（\texttt{=}, \texttt{<>}, \texttt{<}, \texttt{<=}, \texttt{>}, \texttt{>=}）を \texttt{emit\_compare\_and\_consume()} 関数によって解析し、右辺の評価結果とレジスタ間で比較命令（\texttt{cmpr} あるいは \texttt{cmpi}）を発行する。

この段階において、コンパイラは条件が成立したとき（真）の処理ではなく、**条件が不成立（偽）であったときに直後のブロックを飛び越えさせるための「逆条件ジャンプ命令」**を出力する。
具体的には、原始言語側で等号 \texttt{=} が指定された場合、偽のケースは「等しくない」となるため不一致ジャンプ \texttt{jnz} を配置し、不等号 \texttt{<>} の場合は一致ジャンプ \texttt{jz} を出力する。

原始プログラムが \texttt{ELSE} 節を伴う構文である場合は、\texttt{then} 節（真のとき実行される文）のコード生成の直後に、全体の終了位置へと導く無条件ジャンプ \texttt{jmp} 命令を挿入する。
そして、\texttt{then} 節の終端に \texttt{else} 節の開始ラベルを、全体の終端に終了ラベルを出力（\texttt{emit\_label}）することで、if-then-else構造の正しい排他的分岐フローを確立する。

\subsection*{3. while文のコンパイル仕様と繰り返し構造}
予約語 \texttt{WHILE} を検知した場合は、繰り返し処理を実現するために「ループ先頭への巻き戻し構造」を構成しなければならない。
そのため、コンパイラはまず条件式の評価ルーチンへ突入する前に、一意な開始ラベル（\texttt{start\_lbl}）を即座に配置する。
この開始ラベルの直後に条件式を評価させ、if文と同様に \texttt{emit\_compare\_and\_consume()} を用いて比較命令を出力した上で、条件が不成立（偽）となった際に繰り返しを即座に離脱してループ外へ脱出するための逆条件ジャンプ命令を発行する。

この条件評価の関門を突破した（条件成立）とみなされる位置に、ループの本体となる文（\texttt{statement()}）のコードを生成する。
ループ本体ブロックの解析コードの出力がすべて完了した直後、コンパイラは無条件に条件評価の先頭位置へと制御を強制帰還させるための \texttt{jmp [start\_lbl]} 命令を出力する。
最後に、ループ脱出用ジャンプの遷移先となる終了ラベル（\texttt{end\_lbl}）を全体のエピローグとして書き出すことで、条件が真である限りメモリ上を循環し続ける安全な後判定型の繰り返し構造を組み立てている。

\section*{(3) 作成した演算子順位構文解析の仕様}

\subsection*{1. ボトムアップ構文解析の導入背景と設計方針}
本コンパイラでは、数式解析（式評価）の堅牢性を高めるため、システム（C言語）の再帰呼び出しに頼るトップダウン法とは異なり、コンパイラ内部で独立したスタックを明示的に制御する「演算子順位構文解析法（ボトムアップ構文解析）」を数式解析ルーチンとして全面的に採用・実装した。
字句解析から順次渡されるトークンの列を、右から左へとボトムアップに還元（リデュース）していくため、関数 \texttt{parse\_expression\_bottomup()} 内にサイズ256の演算子スタック（\texttt{op\_stack}）と被演算子スタック（\texttt{val\_stack}）をそれぞれ独立して定義した。

\subsection*{2. 優先度関数によるシフト・還元アルゴリズムと優先度表}
構文解析の進行を司るのは、配列として定義された2つの優先度関数、すなわちスタック内演算子の優先度を示す \texttt{rank\_f} と、入力（現在読み込んでいるトークン）の優先度を示す \texttt{rank\_g} である。
指導書の仕様に基づき、各種演算子（加減乗除、カッコ、識別子・定数、式終端の番兵\texttt{\$}）に割り当てた優先度関数の具体的な値を表1に示す。

解析の初期状態では、\texttt{op\_stack} に式の開始と終了を担保するための番兵 \texttt{OP\_END}(\texttt{\$}) を最初の一要素としてプッシュする。
そして、無限ループ内で現在のトークンから入力側の優先度インデックスを抽出し、スタックトップの演算子との間で優先度の高低を比較する。
このとき、入力側のトークンが識別子（\texttt{IDENTIFIER}）または数値（\texttt{NUMBER}）である場合は、それらを即座にレジスタ \texttt{r0} へロードし、一時変数生成関数 \texttt{new\_temp()} によって動的に確保したメモリ番地（\texttt{\_\_tmp0}, \texttt{\_\_tmp1} $\dots$）へと \texttt{store} 命令を介して格納する。この生成された一時変数の記号表インデックス（データ番地）を \texttt{val\_stack} へとプッシュし、字句を消費する。

スタックトップの優先度 $f$ と入力演算子の優先度 $g$ の比較に基づく分岐制御の仕様は以下の通りである。
\begin{itemize}
    \item \textbf{$f < g$ の場合（シフト処理）：} 入力された演算子トークンをそのまま \texttt{op\_stack} へとプッシュし、\texttt{getsym()} を呼び出して次のトークンへ進む。この際、式先頭や開きカッコの直後に現れるマイナス符号を「二項演算の引算」ではなく「符号反転の単項マイナス（\texttt{OP\_UNARY}）」として正しく識別するため、直前にオペランドを消費したかどうかの状態フラグ \texttt{expect\_operand} を用いて厳密に文脈を判定している。
    \item \textbf{$f > g$ の場合（還元処理）：} \texttt{op\_stack} から現在の最優先演算子をポップし、それに対応する仮想マシン \texttt{sr} 用のアセンブリコードを出力するコード生成処理へと移行する。還元（リデュース）の実行時は、入力側のトークンを進めず、同じトークンを維持したまま次回のループで再比較を行う。
    \item \textbf{$f == g$ の場合（特殊解消）：} スタックトップが開きカッコ \texttt{(} であり、かつ現在の入力トークンが閉じカッコ \texttt{)} である場合は、カッコのネストが解消されたとみなし、スタックから \texttt{(} をポップして消去した上で、入力の \texttt{)} を消費して次の字句へ進む。また、スタックトップと入力の双方が番兵 \texttt{\$} に達した場合は、数式全体のパースが正常に完了したと判定してループをブレイクする。
\end{itemize}

\subsection*{3. 還元時におけるコード生成とスタックの連動}
演算子の還元が実行される際、本コンパイラは被演算子スタック（\texttt{val\_stack}）に積まれているメモリ番地情報を引き出し、レジスタ操作命令へと落とし込む。
ポップされた演算子が単項マイナス（\texttt{OP\_UNARY}）である場合、\texttt{val\_stack} から対象のメモリ番地を1つポップして \texttt{r0} にロードする。その後、定数ロード関数 \texttt{emit\_load\_const\_to\_reg()} を介してレジスタ \texttt{r1} に即値 \texttt{-1} を生成し、レジスタ間乗算命令 \texttt{mulr r0, r1} を出力することで安全に符号を反転させる。

一方、加減乗除（\texttt{+}, \texttt{-}, \texttt{*}, \texttt{div}）の二項演算子がポップされた場合は、\texttt{val\_stack} から右辺（\texttt{right}）と左辺（\texttt{left}）の割当メモリ番地を順次ポップする。
そして、左辺の値を \texttt{r0} に、右辺の値を \texttt{r1} にそれぞれロードさせ、演算子種別に応じて \texttt{addr}, \texttt{subr}, \texttt{mulr}, \texttt{divr} 命令を出力する。
いずれの還元処理においても、計算された結果（\texttt{r0} の値）は即座に \texttt{new\_temp()} で払い出された新しい一時変数番地へと \texttt{store} され、その新アドレスが再び \texttt{val\_stack} にプッシュされる。
数式の解析がすべて完了した終端時、\texttt{val\_stack} のトップに残された最終アドレスの値を \texttt{r0} へとロードさせることで、式全体の評価値を \texttt{r0} に確定させる仕様を構築した。

\section*{(4) 作成したトップダウン構文解析による数式処理の仕様}

\subsection*{1. 再帰下降構文解析の設計思想と文法規則の写像}
本コンパイラの初期設計（および数式拡張の基礎実験段階）においては、原始言語の数式規則を最も直感的に展開できる「トップダウン構文解析（再帰下降構文解析法）」による数式処理の仕様を定義した。
この手法は、言語の形式文法（BNF記述や構文図）に定義された非終端記号の階層関係を、C言語の関数呼び出しのネスト構造へダイレクトに1対1で写像（マッピング）させるアプローチである。
これにより、コンパイラはマシンのシステムスタック領域を利用し、再帰的に下位の関数を呼び出しながら構文解析木を暗黙的にトップダウン走査していくことが可能となる。

本仕様では、演算子の優先順位（カッコ \texttt{()} $>$ 乗除算 \texttt{*}, \texttt{div} $>$ 加減算 \texttt{+}, \texttt{-}）を正確に評価・コード生成へと結びつけるため、相互に再帰を繰り返す3つの解析階層関数（\texttt{expression()}, \texttt{term()}, \texttt{factor()}）を定義・実装した。

\subsection*{2. 相互再帰関数群の役割と処理プロセス}
トップダウン数式解析を構成する各関数の詳細な役割と、パース時のアルゴリズム仕様は以下の平文の通りである。

\begin{itemize}
    \item \texttt{void expression(void); } (最上層：式の解析) \\
    加減算（\texttt{+}, \texttt{-}）の結合を管理する関数である。まず内部で下位階層の \texttt{term()} を呼び出して式の左辺項を評価させ、その結果をレジスタ \texttt{r0} に確定させる。
    その後、続くトークンが \texttt{PLUS}(\texttt{+}) または \texttt{MINUS}(\texttt{-}) である間、ループを維持する。
    ループ内では、左辺の結果を破壊しないように一時変数番地（\texttt{new\_temp()}）へ \texttt{store r0} 命令を介して退避させ、字句を進めて右辺全体の評価のために再び \texttt{term()} を呼び出す。
    右辺の評価が \texttt{r0} に完了したのち、退避させていた左辺を \texttt{r1} にロードし、レジスタ間演算命令（\texttt{addr r1, r0} または \texttt{subr r1, r0}）を出力する。
    この累積結果は再び一時変数へと保管され、最終的に \texttt{r0} に結果が戻る。
    
    \item \texttt{void term(void); } (中間層：項の解析) \\
    乗除算（\texttt{*}, \texttt{div}）の結合を管理する関数である。\texttt{expression()} から呼び出され、まず最下位層の因子解析ルーチンである \texttt{factor()} を実行して左辺の因子を \texttt{r0} に評価する。
    続くトークンの属性が \texttt{TIMES}(\texttt{*}) または \texttt{DIV}(\texttt{div}) である限り、ループ処理を行う。
    アルゴリズムの挙動は \texttt{expression()} と同様であり、現在の \texttt{r0} の計算結果を一時変数番地へ退避した上で \texttt{getsym()} を発行し、右辺因子を評価するために \texttt{factor()} を呼び出す。
    右辺因子のパースが完了すると、メモリから値を復元してレジスタ間乗除算命令（\texttt{mulr}, \texttt{divr}）を出力し、階層的な演算順位を保証する。
    
    \item \texttt{void factor(void); } (最下層：因子の解析) \\
    数式を構成する最小単位（因子）を識別する、最も基礎となる関数である。現在のトークンが変数（\texttt{IDENTIFIER}）であれば、\texttt{sym\_lookup()} で割当アドレスを取得して \texttt{load r0, [addr]} 命令を出力する。
    数値（\texttt{NUMBER}）であれば定数合成命令を出力して \texttt{r0} に値を置く。
    もし現在のトークンが開きカッコ \texttt{(} であった場合は、カッコ内の数式が最も高い優先度を持つため、トークンを消費した上で、**最上層の \texttt{expression()} を動的に再帰呼び出し（相互再帰）**する。
    これにより、カッコで囲まれた複雑な数式がどれほど深くネストしていても、独立した部分式として最上層から安全に再パースされ、閉じカッコ \texttt{)} の整合性をチェックして factor 階層を抜ける仕様を確立している。
\end{itemize}

\subsection*{2. レジスタ衝突（物理レジスタの破綻）とスタック退避特性の検討}
目的計算機（仮想マシン \texttt{sr}）のように、利用可能な物理レジスタの数に制限（\texttt{r0} $\sim$ \texttt{r3}）があるアーキテクチャに対してコード生成を行う際、2つの手法ではレジスタ衝突の回避メカニズムに決定的な差異が生じる。

トップダウン法で二項演算を深く入れ子にした式（例：右辺にさらに複雑なカッコ付きの式が続く場合）を愚直にパースしようとすると、下位の再帰呼び出しを処理する過程で、現在左辺の結果を保持しているレジスタの内容が重複して上書きされる「レジスタ破綻」を引き起こす。
これを解決するためには、ソースコードの要所（\texttt{term} や \texttt{expression} のループ内）に変数の値をメモリへ一次退避・復元する退避コードを明示的かつ泥臭く組み込まなければならず、コードの保守性を著しく低下させる。

一方、ボトムアップ法（演算子順位法）では、被演算子トークン（変数・定数）が出現した瞬間に、最初からすべて \texttt{new\_temp()} で動的に生成した一時メモリ空間へと値を退避させ、そのメモリ番地を \texttt{val\_stack} へと積み上げていく。
この設計により、いかにネストが深く複雑な数式であっても、レジスタ操作は還元の瞬間に「スタックから2つのメモリ番地を取り出し、\texttt{r0} と \texttt{r1} に一時的にロードして演算を終えたら直ちに新しい一時メモリへ書き戻す」という定型的なパターンに完全に統一される。
結果として、物理レジスタの消費を最低限の2個（\texttt{r0}, \texttt{r1}）で完全にロックすることができ、コンパイラ側のレジスタ自動割当（アロケーション）ロジックを肥大化させることなく、絶対にレジスタ衝突を起こさない極めて堅牢なコード生成系を確立できるメリットがある。

\subsection*{3. コンパイル時および実行時におけるオーバーヘッドとトレードオフ}
2つの手法のトレードオフ特性について、コンパイルの効率（時間・空間）および生成される目的コードの実行速度という二面性から客観的な比較検討を行う。

トップダウン法は、ネストが深い式になるほどC言語の関数呼び出しの階層が深くなるため、コンパイル時におけるシステムスタックの消費量と、プロローグ・エピローグ処理に伴うコンパイル速度の劣化という「コンパイル時のオーバーヘッド」を伴う。
しかし、出力されるアセンブリコードの観点から見ると、計算途中の値を不必要にメモリへ保存せず、可能な限りレジスタ上で演算を継続するコードを引き出せるため、実行時における \texttt{load}/\texttt{store} 命令の総数が少なく、実行速度の速いコンパクトな目的プログラムを生成しやすい特性を持つ。

これとは対称的に、今回ボトムアップ法で実装したアルゴリズムは、コンパイル処理自体は平坦な無限ループと2つの静的配列スタックのインデックス操作、および定数時間（$\mathcal{O}(1)$）の優先度テーブル参照のみで駆動するため、コンパイル速度自体は非常に高速かつ軽量に動作する。
しかし、その代償として、計算の中間結果をすべて一時メモリを介してリレーする特性上、出力されるアセンブリコード内に \texttt{store r0, [\_\_tmp]} と \texttt{load r1, [\_\_tmp]} というメモリメモリアクセス命令が大量に乱発される。
これは、目的計算機シミュレータ上での実行時に「メモリバスアクセスの過多」を引き起こし、ステップ数の増大と実行速度の低下（実行時オーバーヘッドの累積）を招く要因となる。

この比較検討から、限られた目的アーキテクチャにおいて、レジスタの破綻を100\%確実に回避できる「ボトムアップ法によるコンパイル安全性の獲得」と、生成される「目的プログラムの実行速度効率」の間には、明確なトレードオフ（相克関係）が存在することを実証的に確認することができた。

\section*{(6) 手続きの実現の仕様}

\subsection*{1. 現在までに実装を完了した手続き処理の枠組み}
本コンパイラの実装実験においては、高水準言語における手続き（\texttt{procedure}）の宣言、および引数を伴う手続き呼び出し（\texttt{call}）を実現するための構文解析と基礎的なコード生成系の枠組みを構築した。

大域的な構文解析を司る \texttt{outblock()} 関数内において、予約語 \texttt{PROCEDURE} を検知した際、コンパイラは手続き宣言ブロックの解析へと遷移する。
まず字句解析から手続き名（識別子）を取得し、これを \texttt{sym\_install()} によって記号表に登録した上で、制御用ラベル生成関数 \texttt{new\_label()} を用いてその手続き専用の開始ラベル（\texttt{lbl}）を割り当てる。
この開始ラベル情報は、並列マッピング配列 \texttt{proc\_label} へと安全に退避される。
続いて、仮引数のリストを解析する専用ルーチン \texttt{paramlist(PARAM\_DECL)} を呼び出し、手続きが要求する引数情報を記号表へとマッピングする。その後、手続き本体を処理するために \texttt{inblock()} を再帰的に呼び出すことで、手続きの包含関係をトップダウンにパースする機構を確立した。

一方、文の解析を行う \texttt{statement()} 関数内で識別子が出現し、かつ直後に開きカッコ \texttt{(} を検知した場合は、代入文ではなく手続き呼び出し（関数実行）であると判定する。
この際、実引数リストを評価する \texttt{paramlist(PARAM\_CALL)} を起動させ、現れた実引数（数式）をボトムアップ数式解析ルーチンを介して評価したのち、目的計算機のスタック領域へと順次プッシュするアセンブリコードを生成する。
実引数の解析がすべて完了して引数の総数（\texttt{argc}）が確定した直後、コンパイラは \texttt{proc\_label} から該当手続きの開始ラベルを逆引きし、仮想マシンに対するサブルーチン分岐命令である \texttt{call L[lbl]} 命令を出力する。
呼び出しから制御が復帰した直後には、スタックに積んだ実引数領域をクリアしてメモリポインタを正常に戻すため、スタックポインタを引数分だけ引き上げる \texttt{addi sp, argc} 命令をエピローグとして出力する仕様を実装した。

\subsection*{2. 現状の実装における構造的課題と再帰呼び出しの制限}
上述の通り、手続きの「宣言のパース」と「呼び出し時のジャンプ命令・引数のプッシュ」という基本的なシーケンスは正常に機能している。
しかし、この仕様のままでは、手続きが自分自身を重ねて呼び出す「再帰呼び出し（\texttt{Recursive Call}）」を実行した際、実行時の計算不整合が発生するという致命的な制限を抱えている。

その根本原因は、現在の変数参照がすべて記号表のインデックス番地（固定番地アクセス）に依存している点にある。
現状の実装では、手続き内で宣言された仮引数や局所変数であっても、すべて大域変数と同様の固定メモリ番地に対して \texttt{load}/\texttt{store} 命令が発行されてしまう。
このため、手続きが再帰的に多重呼び出しされた場合、後から実行された世代の処理によって、先行する親世代が保持していた局所変数の値がメモリ上で直接上書きされ、破壊されてしまう。
手続き処理を完全に実現し、再帰呼び出しを保証するためには、実行時環境（\texttt{Runtime Environment}）の抜本的な拡張が不可欠である。

\subsection*{3. 再帰呼び出しの完全成立に向けたスタックフレームの発展設計仕様}
多重の再帰呼び出しに耐えうる手続き処理を完成させるためには、すべての仮引数および局所変数を固定番地ではなく、**実行時スタック上に動的に確保されるスタックフレーム（活性レコード）内の相対番地**として管理しなければならない。

今後の具体的な発展設計仕様として、目的計算機が持つベースレジスタ（\texttt{BR}）をフル活用する仕組みを導入する。
手続きが呼び出された直後のプロローグ（前処理）において、現在の \texttt{BR} の値をスタックに退避させ（動的リンクの保存）、現在のスタックポインタ（\texttt{SP}）の値を新たな \texttt{BR} にコピーして、その関数世代の基準点を確立する。
これにより、手続き内の引数や局所変数は、すべて基準点からのオフセット、すなわち \texttt{load r0, -4(BR)} や \texttt{storer r0, 1(BR)} のようなベースレジスタ相対ロード・ストア命令（\texttt{loadr}, \texttt{storer}）を介してアクセスされる仕様へと変更する。
このとき、記号表側も前述の二重構造へと拡張し、インデックス番号の代わりに「\texttt{BR} からの相対オフセット値」を属性として保持する仕様へと作り変える。

手続きの終了時（エピローグ）には、スタックから元の \texttt{BR} の値をポップして書き戻し、親世代の基準点を完全に復元した上でサブルーチン復帰命令（\texttt{ret}）を実行する。
この動的なスタックフレーム制御の導入により、同一の手続きが何世代にわたって再帰呼び出しされようとも、各世代の変数はメモリスタック上の異なるフレーム領域に隔離され、値の破壊が一切起きない堅牢な手続きシステムが完成する。

\section*{(7) エラー処理について}

\subsection*{1. コンパイラにおけるエラー処理の基本方針と設計思想}
コンパイラ開発において、不完全または文法的に破綻した原始プログラムを検知した際の振る舞いは、システムの堅牢性を左右する重要な設計要素である。
本コンパイラでは、不適切なソースコードを検知した際、誤ったアセンブリコードを出力したまま処理を継続することを防ぎ、目的計算機シミュレータへの汚染を防ぐため、\textbf{「パニックモード一律停止型」のエラー処理アルゴリズム}を採用している。

エラー処理の基盤として、ソースファイル内で \texttt{error(char *s)} 関数を一元定義している。
構文解析のいずれのフェーズであっても、矛盾や文法規則違反を発見した瞬間にこの関数が呼び出される。
関数内部では、引き渡されたエラー原因を示すメッセージ文字列を \texttt{fprintf(stderr, ...)} 命令を介して標準エラー出力へと明示的に書き出す。
その後、目的プログラムであるアセンブリファイル（\texttt{outfile}）の出力を即座に遮断し、C言語の標準ライブラリ関数である \texttt{exit(1)} を実行してコンパイルプロセスそのものを直ちに異常終了（強制パニックアウト）させる仕様としている。
これにより、異常な原始プログラムから不正なアセンブリコードが生成されてしまう不整合を完全に防止している。

\subsection*{2. 各コンパイルフェーズにおける具体的なエラー検知メカニズム}
本コンパイラが原始プログラムを走査する際、検知対象となるエラーは、その性質に応じて字句・構文・意味解析の3つの階層に分類され、それぞれ異なる関数フックで厳密に補足される。それぞれの詳細な仕様を以下に記述する。

\begin{itemize}
    \item \textbf{構文解析階層における記号・予約語の欠落フック：} \\
    プログラム全体の枠組みを定義する \texttt{compiler()} や、制御構文・ブロックを処理する \texttt{statement()}、変数宣言を行う \texttt{outblock()} 内で主に作動する。
    例えば、プログラム名宣言直後のセミコロン（\texttt{;}）の欠損、\texttt{begin} に対応する \texttt{end} キーワードの不在、\texttt{if} 条件文の直後に現れるべき \texttt{then} の欠落、あるいはボトムアップ数式解析中に開きカッコ \texttt{(} と閉じカッコ \texttt{)} の不整合が起きたケースである。
    これらはトークンの属性（\texttt{tok.attr}）や値（\texttt{tok.value}）を予測される文法規則と比較し、合致しない場合に「\texttt{then が必要です。}」といった具体的なメッセージを伴って \texttt{error()} へ移行する。
    
    \item \textbf{意味解析階層における未定義識別子の参照検知：} \\
    代入文の左辺、数式内の変数出現時、または手続き呼び出し時において、記号表（シンボルテーブル）の検索ルーチンである \texttt{sym\_lookup(tok.charvalue)} と連動して作動する。
    原始プログラム内で事前に宣言（\texttt{var}）されていない識別子を参照しようとした場合、\texttt{sym\_lookup()} は未登録のシグナルとして \texttt{-1} を返却する。
    コンパイラはこの戻り値を検知した瞬間に「\texttt{未宣言の変数に代入しようとしています。}」または「\texttt{右辺の変数が未定義です。}」というエラーを発行し、不正なメモリ番地へのアクセス命令がアセンブリコードに出力されるのを未然に遮断する。
    
    \item \textbf{目的計算機アーキテクチャの制約に起因する即値限界エラー：} \\
    定数ロード関数 \texttt{emit\_load\_const\_to\_reg()} 内部において、ハードウェアの即値上限に起因して作動する特殊な意味エラーである。
    目的計算機の \texttt{loadi} 命令が持つオペランドは 16bit 領域（$-32768 \sim 32767$）に制限されている。
    本コンパイラでは、この制限を超える巨大な定数が現れた際、自動的に2つの整数の積へと因数分解して命令を合成する拡張ロジックを実装しているが、万が一分解不可能な巨大な素数などが現れて合成に失敗した場合、そのままでは異常な機械語が生成されてしまう。
    これを防ぐため、因数分解ループを抜けた最終エピローグ領域に「\texttt{定数が大きすぎて処理できません。}」というトラップを配置し、アーキテクチャの破綻をコンパイル時に検知して安全に停止させる仕様としている。
\end{itemize}

\subsection*{2. 実現した各解析関数の依存関係図（コールツリー）}
コンパイラ内部における各解析関数の呼び出し関係（コールツリー）および、トップダウン制御とボトムアップ数式解析が融合したハイブリッドな依存関係を図10に示す。

プログラム全体の解析エントリポイントは \texttt{compiler()} である。
\texttt{compiler()} は起動直後に \texttt{init\_getsym()} を介して字句解析を初期化し、プログラム頭部の宣言を確認したのち、変数宣言ブロックを解析する \texttt{outblock()} を呼び出す。
\texttt{outblock()} は \texttt{var} キーワードが続く限りループを維持して大域変数を記号表へ蓄積し、変数宣言の完了直後に \texttt{sym\_dump()} をキックして記号表の全状態をデバッグ用に書き出す。

続いて、プログラム本体の文解析を行うために最上層の文パース関数 \texttt{statement()} が呼び出される。
\texttt{statement()} はプログラムの入れ子構造をパースするため、予約語 \texttt{BEGIN} を検知した際には自分自身を再帰的に何度も呼び出す（自己再帰）。
また、代入文（\texttt{IDENTIFIER :=}）や制御構文（\texttt{IF}, \texttt{WHILE}）の分岐条件式に遭遇した際には、式評価の統合ラッパーである \texttt{eval\_to\_r0()} を呼び出す。

本コンパイラ仕様の最大の特徴は、この \texttt{eval\_to\_r0()} の下位の依存関係にある。
従来の再帰下降（トップダウン）用の3関数 \texttt{expression()}, \texttt{term()}, \texttt{factor()} への依存関係は安全のために遮断（コメントアウト）されており、代わりに2つの明示的スタックをループ制御するボトムアップ式解析関数 \texttt{parse\_expression\_bottomup()} へと制御が一方向へ委ねられる。
\texttt{parse\_expression\_bottomup()} の内部では、数式の還元に伴ってアセンブリコード生成系や一時変数割当（\texttt{new\_temp()}）が呼び出され、最終的な評価値をレジスタ \texttt{r0} に確定させて \texttt{statement()} の制御へと安全に復帰する。

\section*{(11) その他、工夫した点について}
\subsection*{大きな定数（即値）への対応自動化 (\texttt{emit\_load\_const\_to\_reg})}
目的計算機仕様において、即値ロード命令（\texttt{loadi} 等）のオペランドが 16bit（$-32768 \sim 32767$）に制限されている制約に対して工夫を行った。
ソースコード中に制限を超える大きな定数が現れた際、コンパイラが自動的にその数値を因数分解（16bit以内に収まる2つの整数の積に分解）し、
レジスタ上で \texttt{loadi} 命令と \texttt{muli} 命令を動的に組み合わせて目的の定数値を合成する関数 \texttt{emit\_load\_const\_to\_reg} を独自に設計・実装した。
これにより、人間が手動で定数を分割定義することなく、巨大な定数を含む複雑な数式であっても安全にコンパイルを通すことが可能となった。

\subsection*{静的変数を用いた再帰深度の動的追跡と halt 命令の一意出力制御}
本コンパイラの文解析ルーチン \texttt{statement()} の実装において、
プログラムの正常終了を司る \texttt{halt} 命令を「いかにしてアセンブリコードの真の最外層の終端にのみ1回だけ一意に出力させるか」という、
コード生成制御上の課題に対して独自の工夫を行った。

高水準言語における \texttt{BEGIN ~ END} ブロックや \texttt{IF}, \texttt{WHILE} などの制御構文は、
内部に別の文を内包するため、\texttt{statement()} 関数が自分自身を何度も呼び出す「自己再帰構造」を形成する。
もし単純に関数のエピローグ領域へ \texttt{halt} 命令の出力を記述してしまうと、
入れ子構造の内側にある部分的な文の解析が完了して再帰スタックから復帰するたびに、
アセンブリコードの途中に \texttt{halt} が不当に乱発され、シミュレータ上でプログラムが途中で強制終了してしまう破綻を招く。

この課題をスマートに解決するため、C言語の \texttt{static} 変数の特質を応用した「再帰深度カウンタ」のロジックを関数内に独創的に組み込んだ。
具体的には以下の制御シーケンスを実装している。
\begin{lstlisting}[language=C, basicstyle=\small\ttfamily]
static int depth = 0;
int is_outer = (depth == 0); /* 最外層エントリポイントの判定 */
depth++;

/* --- 各種文（BEGIN, IF, WHILE, 代入文等）の構文解析とコード生成 --- */

depth--;
if (is_outer) {
    fprintf(outfile, "halt\n"); /* 真の最外層終端でのみ1回だけ出力 */
}
\end{lstlisting}

このアルゴリズムにより、コンパイラが最初にプログラム全体の文解析へ突入した最初の一歩（深度0）のタイミングでのみ、
ローカルフラグ \texttt{is\_outer} に「真（1）」がロックされる。
その後、どれほど深く \texttt{BEGIN} のネストが繰り返されてスタックフレームが積み上がろうとも、
内側の呼び出し世代においては \texttt{depth > 0} となるため、フラグは一律で「偽（0）」に固定され、不要な \texttt{halt} の出力を完全に抑制する。

そして、すべての構文解析が完了して再帰のネストが完全に巻き戻り、まさに「プログラム全体の解析を終えて脱出する最後の瞬間」にのみ、
保持されていた \texttt{is\_outer} の条件が成立し、アセンブリの最末尾にのみ美しい \texttt{halt} 命令を1発だけ書き出す制御に成功した。
コンパイラ全体のコード生成構造を肥大化させることなく、関数ローカルなスコープ内で再帰のライフサイクルを動的に追跡して目的コードの整合性を担保した、
開発時の苦悩と試行錯誤が生んだ極めて実践的なアプローチである。
